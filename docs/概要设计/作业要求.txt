一、作业定位
大作业一已完成《需求规格说明书》，解决了"做什么"的问题。大作业二要解决"怎么做"的总体问题——在需求的基础上完成系统的概要设计，给出系统总体结构、模块划分、接口设计、全局数据设计，并对所提架构方案进行轻量级架构评估。概要设计是需求与详细设计之间的桥梁，决定了系统的骨架。

本次作业以小组为单位完成，提交一份《概要设计说明书》。

二、阶段边界声明（重要，请先读）
本课程按"需求分析 → 概要设计 → 详细设计"三阶段组织大作业：

大作业一（需求规格说明书） 已完成用例建模、活动建模、概念类建模、状态建模与分层数据流图等分析模型。
大作业二（概要设计说明书） 聚焦体系结构、模块划分、接口设计、全局数据设计、运行时协作与架构评估。其建模部分要求完成分析模型向设计模型的转换（设计类图、关键类状态设计、系统级 DFD、关键运行时时序图），不重复需求阶段的用例图、用例详述与活动图，但须在追溯矩阵中引用其编号。
算法、伪代码、完整表字段、代码级函数签名、SQL 语句、模块内部流程等详细设计内容不在本次范围。
各节中凡标注 ⚠️ 边界声明 处，为该节内容的硬性边界，越界内容不计分。

三、总体要求
必须选用一个概要设计说明书模板（推荐国标 GB/T 8567 相关章节结构，或与大作业一模板对应的设计文档版本），在模板基础上填写修改，不得随意删除模板中的章、节。确实不适用的章节，保留标题并注明"本章节不适用，原因：……"。
设计必须可追溯到需求：每个模块、接口、数据策略、架构故事，都应能对应到大作业一中的功能需求或非功能需求编号，并在第 9 节追溯矩阵中体现。
设计必须覆盖非功能性需求：性能、安全、可靠性、可维护性、可移植性等，要在总体架构、模块设计、存储策略、部署设计中体现落实方案，不能只字不提。
文档需结构完整、图表规范、术语前后一致；图表须有编号和标题，正文须引用图表编号。
建模图须使用规范建模工具（Visio、draw.io、StarUML、PlantUML 等），不接受手绘拍照。
四、内容要求
引言与总体设计
编写目的、背景、术语定义、参考资料
需求概述（简要回顾，不重复大作业一全文）
设计原则与约束（可追溯性、高内聚低耦合、非功能需求落实策略等）
总体架构设计与评估（本次作业重点）
2.1 架构设计
2.1.1 架构风格选择与理由：说明所选架构风格（分层/客户机-服务器/微服务等）及选择依据。
2.1.2 系统总体结构图：模块层次图或架构图。
2.1.3 关键架构决策说明：每个决策对应哪些质量属性目标，标注对应需求编号。
2.2 架构故事（支撑场景描述）
选取 3–5 个核心质量属性场景，以叙事方式描述。每个故事必须包含 ATAM 场景的六要素：刺激源、刺激、环境、制品、响应、响应度量。示例格式：

故事 1（性能）：在考试报名高峰期，500 名学生同时提交选课请求，系统应在 3 秒内完成每笔请求的处理并返回确认结果，不得出现超时或数据不一致。
要求：每个故事对应大作业一中至少一条非功能需求，标注需求编号。

2.3 轻量级 ATAM 评估
说明：完整 ATAM 需 3–4 天、多类利益相关者参与。课程作业只要求模拟其核心分析逻辑，不要求模拟完整评审会议流程。评估对象是 2.1 中已提出的架构方案，顺序必须是：设计 → 讲故事 → 建效用树 → 分析 → 给改进建议。
2.3.1 质量属性效用树：以"效用"为根，性能/安全/可用性/可修改性等为一级节点，展开到具体场景（即 2.2 的故事），标注重要性（H/M/L）和实现难度（H/M/L）。
2.3.2 架构方法识别与分析：针对效用树中高优先级场景，说明现有架构设计采用了什么方法应对，分析其效果。
2.3.3 评估发现：
风险点：可能削弱某质量属性的架构决策。格式要求："决策 + 论证 + 质量影响"，例如"模块 A 与模块 B 采用同步调用（决策），在峰值负载下可能造成请求堆积（论证），削弱响应时间达标能力（质量影响）"。不得只写"性能可能不足"。
非风险点：对质量属性有正面影响的决策。
敏感点：对某个质量属性影响显著的决策。
权衡点：同时影响多个质量属性、需要折中的决策。
2.3.4 评估结论与改进：基于上述发现，对架构设计提出 1–3 条具体改进建议，并说明是否已反映在 2.1 的设计中。
模块设计与逻辑架构
3.1 包图/组件图与分层划分：给出系统的包图（Package Diagram）或组件图（Component Diagram），清晰展现系统各层（如展现层、业务逻辑层、数据访问层）的逻辑划分。
⚠️ 边界声明：本层次只到"包/组件"粒度，不展开包内类清单与类内部实现。
3.2 模块职责与功能分配：逐个说明各模块/子系统的职责、输入输出，并标注其对应的大作业一功能需求编号。
3.3 模块间接口契约（概要级）：说明主要模块之间的调用关系与接口契约，列出接口名称、功能描述、核心输入/输出大类、协议类型。完整接口定义见第 5 节。
⚠️ 边界声明：不编写代码级函数签名，不贴具体 JSON 样例。
设计模型（分析模型 → 设计模型转换）
本节要求在大作业一分析模型基础上完成面向设计的转换。需求阶段已有的用例图、用例详述、活动图不要求重复绘制，但需在追溯矩阵中引用其编号。
4.1 核心设计类图（粗粒度）：基于概念类图转换为设计类图，重点展示核心边界类、控制类、关键实体类及其依赖、聚合、泛化关系，标注多重性；明确类职责、主要属性与关键业务方法（方法可只列签名，不展开算法）。
⚠️ 边界声明：禁止写出所有私有变量、辅助方法或大量 getter/setter（属详细设计）。
4.2 关键类状态设计：选取状态变化最复杂的 1 个类，给出状态图，说明状态、事件、迁移及守卫条件。此为状态级设计，不展开状态内行为实现。
4.3 系统级数据流图：在需求阶段分层 DFD 基础上，给出系统级数据流图（顶层 + 第一层），标注各加工对应的模块，体现"数据流 → 模块"的映射。注意父子平衡（顶层与第一层输入输出数据流一致）。
4.4 关键运行时设计：系统级时序图：绘制 2–3 个系统级时序图（Sequence Diagram），展示模块/组件之间在运行时的调用顺序、消息传递与控制流。
要求：必须从 2.2 架构故事所对应的高优先级场景中选取，每个时序图标注对应的故事编号与效用树叶节点，与 2.3 的 ATAM 评估形成闭环。
⚠️ 边界声明：时序图以模块/组件为生命线，不画到类方法级调用，不展开循环与条件内部的算法细节。
接口设计
本节聚焦系统骨架的对接契约，明确"谁在和谁通信"以及"通信的规约是什么"。
5.1 外部接口设计：
用户界面接口：系统与用户交互的输入输出设备及逻辑风格（如 Web 端/移动端/大屏展示）。
硬件接口与软件接口：系统与外部硬件（如读卡器、生物识别仪）或第三方软件系统（如微信支付 API、国家认证中心数据源）的连接协议与交互方式。
5.2 内部系统级接口设计：系统内部主要子系统或核心模块之间的 API 契约（如前后端 RESTful API 路由定义、微服务间 RPC 接口描述）。列出接口名称、功能描述、核心输入参数大类、核心返回数据大类、协议类型（如 HTTP/JSON）。
⚠️ 边界声明：不要编写具体的代码级函数签名，也不要贴出冗长的具体 JSON 样例。
数据设计与存储策略
6.1 全局数据逻辑结构设计：给出系统级的高层实体关系图（高级 ER 图），厘清核心全局实体的关联。
6.2 概要级表结构设计：列出主要数据表/数据结构的概要设计（表名、主要字段、主外键）。
⚠️ 边界声明：严禁出现具体的 CREATE TABLE 等 SQL 语句，也无需列出每个表的完整字段清单（字段字典留到详细设计完成）。
6.3 存储方案与物理策略：
明确各类数据采用的存储技术（如关系型数据库 MySQL、非关系型缓存 Redis、对象存储 OSS 等）及选型理由。
说明全局数据的拓扑结构策略（如是否采用读写分离、主从复制、数据分片、全局唯一 ID 生成策略等）。
设计高并发或大数据量下的缓存更新策略与一致性保障机制。
⚠️ 边界声明：本节属于逻辑与策略设计，不涉及具体配置参数与部署脚本。
部署设计
7.1 部署图：绘制系统的部署图（Deployment Diagram）。
7.2 物理部署架构说明：明确系统在物理或云环境中的拓扑结构，包括服务器节点（应用服务器、数据库服务器、网关、负载均衡器等）的配置映射、网络隔离（如 DMZ 区、内网区）以及网络协议。
非功能需求的实现方案
逐条说明性能、安全、可靠性、可维护性等需求在架构与模块设计中如何落实（与第 2 节 ATAM 评估相互呼应）。

需求编号（来自大作业一）	需求名称	对应架构故事/决策编号	对应设计模块/类	对应内部/外部接口	对应全局数据实体

七、常见问题提醒
包图不是类图：第 3 节只到包/组件粒度，类清单与类内部实现属第 4 节与详细设计。
类图不是数据库表：第 4.1 节设计类图阶段不要出现外键字段，先做设计建模，第 6 节再做 ER 与表结构。
状态图别画成流程图：描述"对象处于什么状态、什么事件触发迁移"，不是步骤顺序。
数据流图注意平衡：顶层图与第一层分解图的输入输出数据流必须一致（父子平衡）。
时序图不是用例基本流复述：必须从 2.2 架构故事中选取高优先级场景，标注故事编号，否则不加分。
ATAM 评估不能倒序：不能先写评估结论再补架构设计，必须"设计 → 评估"。
架构故事不是用例：用例描述"用户做什么、系统怎么响应"；架构故事聚焦"刺激—响应—度量"的质量属性维度。一个用例可能对应多个架构故事。
风险必须带论证：格式"决策 + 论证 + 质量影响"，只写"可能性能不足"不得分。
边界声明是硬约束：凡标 ⚠️ 处出现的越界内容（getter/setter 清单、CREATE TABLE、代码级签名、长 JSON 样例）不计分。
追溯矩阵不是形式主义：评阅时会抽查"需求编号 → 模块/接口/数据实体"的对应是否真实成立。
